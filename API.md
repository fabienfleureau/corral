# Corral HTTP API contract (v1)

Base: `http://127.0.0.1:4787`. Auth: every `/api/*` route except `/api/health` requires
either `Authorization: Bearer <token>` or the `corral_token` cookie. The web app is
served at `/`; visiting `/?token=<token>` sets the cookie and redirects to `/`.
On 401 the UI shows a token-entry screen (send the token as `?token=` once).

Live updates: `GET /api/events` (SSE). Events: `event: item.created|item.updated|task.updated|session.updated|pulls.updated`
with the entity JSON as `data`. Use `item.created` for desktop notifications.

Page-load endpoints never wait on a third party indefinitely: per-session lookups give up
after 3s (`/api/tasks`), the session list after 4s, the harness registry after 6s, and the
OpenCode Go quota after 2.5s and Google quota (Antigravity) after 10s. The response then carries last-known data or a note, so a
stalled dependency degrades the page instead of hanging it.

Static hosting: `/assets/*` (Vite content-hashed) is `Cache-Control: public, max-age=31536000,
immutable`; the shell, `sw.js` and the other root files are `no-cache` with an `ETag`, so a
reload is a 304 unless a deploy replaced them.

Unknown `/api/*` paths answer `404 {"error":"unknown endpoint: <METHOD> <path>"}`. The SPA
shell is never served under `/api/*`, so a server older than the page reports a missing
endpoint instead of returning HTML the client would fail to parse.

## Entities

```ts
type Task = {
  id: string; title: string; prompt: string; repo_path: string;
  kind: "code" | "review" | "spec" | "analysis" | "ops" | "grill" | "grill-docs"; // review: review pr_url; spec: folder of sub-projects; ops: work in a folder and report back. grill/grill-docs interview in a folder or repo. review/spec/analysis/ops/grill have no branch or PR loop
  parent_task_id: string | null; // the spec task a code task was created from; its contract is appended to the prompt at dispatch
  spec: string | null;        // spec tasks: JSON {contract, subtasks:[{repo,title,prompt}], revision_id?, version?, children?}
  pr_url: string | null;      // the task's PR, or the reviewed PR/MR for kind "review"
  review: string | null;      // resolved review command, frozen at dispatch (code tasks)
  target: string;             // "", "claude", "codex", "opencode"
  target_state: "suggested" | "confirmed";
  base_branch: string | null; branch: string | null; worktree_path: string | null;
  assignee: string | null;
  jira_key: string | null; jira_url: string | null; jira_parent_key: string | null;
  jira_status: string | null; // Jira status last reached by the status sync (cached; written by the sync)
  status: "open" | "dispatched" | "done" | "archived";
  terminal_address: string | null; exit_code: number | null;
  created_ms: number; updated_ms: number;
};

type Item = {
  id: string;
  kind: "question" | "pr" | "digest" | "plan" | "launch" | "amendment"; // launch: a task whose epic prerequisites are ready
  status: "open" | "resolved" | "archived";
  title: string;
  summary: string;   // structured summary ("" until summarized)
  body: string;      // raw tail / structured body — shown when summary is empty
  source_ref: string | null;   // herdr terminal address for question items
  task_id: string | null;
  structured: number;          // 1 = agent reported it, 0 = fallback: the session blocked, or its run ended (idle/error) with no report
  ready: number;               // pr items: 1 = review gate passes (threads resolved, checks green)
  handling: number;            // pr items: 1 = the agent has the PR work in flight
  created_ms: number; updated_ms: number;
  resolved_ms: number | null; snooze_until_ms: number | null;
  snooze_count: number;         // times the human snoozed it; 2+ shows "snoozed N×" and sorts first
};

```

## Endpoints

### KPI monitoring

The contract types live in [`shared/kpis.ts`](shared/kpis.ts). Supported IDs are
`kpi-1` and `kpi-2`. Both slots start empty.

- `GET /api/kpis` → `KpiView[]` — settings, cycle state, Omnigent session link, latest validated report, last sourced measurement, up to 60 past measurements (one per window, oldest first) and, with a goal, `goalProgress` (`baseline`, `gap`, `progress`, `reached`) for both KPIs. This reads SQLite.
- `PUT /api/kpis/:id` `{name, definition, unit, sources, repoPath, favorite, intervalHours, context, goal}` → `KpiView` — saves the metric definition, its optional display unit and source references, then the agent settings and operator context. `repoPath` is any absolute folder, git repository or not; the session runs there directly, without a worktree. The session is filed into the same Omnigent project as task sessions for a registered folder; an unregistered folder uses its path as the project name. `favorite` names a configured favorite whose harness, agent, model and reasoning are used for the cycle; it must match the folder's context (an unregistered folder uses professional). A schedule (1 hourly, 24 daily, 0 off) requires a name, definition, folder and favorite. Settings saved before favorites stored `agent`, `harness` and `repo`; the folder carries over and a favorite must be picked again. Changing the definition or unit resets the previous report and the measurement history, and is allowed between cycles. `goal` is `null` or `{target, direction: "increase"|"decrease", deadline: "YYYY-MM-DD", why}`; a new goal takes the last measurement as its baseline (or the next sourced one), editing it keeps the baseline, and `null` clears both. 400 for invalid settings, 404 for an unknown slot.
- `POST /api/kpis/:id/run` `{instruction?}` → `202 KpiView` — starts one cycle using saved settings. Optional `instruction` (string, up to 6000 characters) is sent once for this cycle only (never saved in settings) so the agent addresses it and folds durable answers into its memory file. 400 for an invalid instruction, 409 when required settings are missing or a cycle is active, 404 for an unknown KPI.
- `POST /api/kpis/:id/artifact` `{format, axes, audience}` → `202 {task}` — starts a Claude `ops` task that builds a **private** artifact from the saved reports and reports its URL to the inbox. `format` is `one-page` (default in the UI) or `slides`; `axes` names the sections to include (the four core sections are always added); `audience` is an optional note under 500 characters. The KPI's favorite is reused when it uses the Claude harness, otherwise the first Claude favorite in the folder's context is used. 400 for an invalid request, 404 for an unknown KPI, 409 when the KPI has no report, no working directory or no Claude favorite.

A report includes the summary, optional numeric measurement with UTC window
and source references, data needs, product questions, proposals with evidence,
and a research memory. The memory shown is a bounded copy of
`.corral/kpi-<slot>-memory.md` in the KPI's working directory. Corral creates the
file from the stored memory on first use; the agent updates it during a cycle
and it becomes the source for the next cycle. A missing measurement is `null`.
A failed cycle leaves the previous report available.

### Daily activity
- `GET /api/daily?start=<ms>&end=<ms>` → task history events in the half-open timestamp interval, joined to registered professional repositories (including legacy null contexts). Each event carries the task title, prompt, repo name/path, Jira and PR links, terminal address and `session_url` (omnigent's session inspect URL when available). The interval must be positive and at most 25 hours. Tasks with an unknown repository are excluded.
- `POST /api/daily/summarize` `{start, end, date, favorite}` → `{task}` — starts an `analysis` task that summarizes the day's activity and reports the markdown to the inbox. `favorite` must name a configured professional favorite; its harness, agent, model and reasoning are used for the dispatch. The task runs without a worktree in the repository of the day's first event. 400 for an invalid interval/date/favorite, 409 when the day has no activity.

### Inbox
- `GET /api/items?status=open|resolved|archived&kind=question|pr|digest|plan|launch|amendment` → `Item[]` (newest first)
- `POST /api/items/:id/reply` `{text}`, `{permission}`, or `{content}` → `{ok, sent_to, item}` — replies to the agent and clears any snooze. For `pr` items, sets `handling: 1` (moving the item to In progress until the run ends); for other items, resolves the item and reopens a `done` task to `dispatched` so it appears in In progress. For structured question batches, `content` maps each question ID to a string (single choice/custom answer) or nonempty string array (multiple selections); every question must be answered. Single-choice questions also accept `{text}`. Permission choices are `approve`, `reject`, `session`, or `always`; scoped choices require an offered pattern. 400 for invalid/incomplete answers; 409 if no terminal is linked or the elicitation item is not open.
- `POST /api/items/:id/summarize` → `Item` — LLM summary of `body` into `summary` (async, may take ~10s)
- `POST /api/items/:id/resolve` → `Item` — the inbox labels this action **Acknowledge**; the stored status stays `resolved`
- `POST /api/items/:id/archive` → `Item`
- `POST /api/items/:id/snooze` `{until_ms?}` → `Item` (default +1h); increments `snooze_count`
- `POST /api/prs/sync` → `{ok, ran}` — starts a background re-check of every dispatched/done task with a known PR (throttled to once per 30s; `ran: false` when skipped). A merged PR completes the task and archives all its items; a closed one resolves the PR item. Updates are broadcast as PRs are re-checked. Each successful check also stores the last observed state in the task's `pr_meta.pr` (`state`, `mergeable`, `checks`, unresolved `threads` ids/count, readiness `reasons`, `checked_ms`) without changing `updated_ms`; it is evidence for the improvement digest, not task activity.

### Tasks
- `GET /api/harnesses` → `{harnesses, agents}` — available harness groups, their model catalogs (when supported by the worker), and the full worker agent registry. 504 when the worker backend does not answer within 6s (retry shortly).
- `GET /api/tasks?status=open|dispatched|done|archived` → `(Task & {session_model: string | null, session_reasoning: string | null, attachment_count: number})[]` — linked session settings reported by the worker, or null when unavailable; `attachment_count` is the number of files attached to the prompt. A session the worker reports as `finished` is read once and kept (see `server/session-facts.ts`); live sessions — including a `done` task whose session is still running — are refreshed through one shared pass per burst of requests, so a queue of a few hundred tasks answers in milliseconds instead of one round trip per task
- `POST /api/tasks` `{title?, prompt?, kind?, pr_url?, repo_path?, target?, model?, reasoning?, base_branch?, assignee?, jira_key?, jira_url?, jira_parent_key?, attachments?}` → `Task` — title or prompt required; an empty title is filled from the omnigent session title after dispatch. `kind: "review"` requires `pr_url` (GitHub pull or GitLab MR URL); the title defaults to `Review <pr_url>`. `kind: "spec"` (multi-repo) requires a prompt and `repo_path` = an existing folder (not a git repo) holding the sub-projects; `kind: "ops"` requires a prompt and an existing folder used as context — no worktree, branch or PR, the agent reports back to the inbox. `grill` and `grill-docs` need a prompt and accept any existing folder in `repo_path`, git repo or not; `grill` interviews in place, `grill-docs` writes docs in a worktree and prepares a PR when the folder is a git repo, otherwise it edits the folder in place and reports without a PR
- `POST /api/tasks` `attachments: {filename, content_type, data}[]` — files for the prompt, `data` base64. At most 10 files and 25 MB together; per file 5 MB for a PNG, JPEG, GIF or WebP image, 20 MB for a PDF, 10 MB for text or code (an SVG counts as text; the extension rescues a text file the browser mislabelled). Checked before anything is stored, so a bad file creates no task: 415 for an unsupported type, 413 for a size, 400 for a malformed entry. Stored with the task and sent to the agent with the first prompt at dispatch (omnigent uploads each file to the session and references it from the message as `input_image` / `input_file`). This is the one route whose request body may exceed 2 MB (about 34 MB)
- `GET /api/tasks/:id/attachments` → `{id, task_id, filename, content_type, bytes, created_ms}[]` — the task's attachments in drop order, without their bytes. 404 for an unknown task
- `GET /api/tasks/:id/plan-revisions` → `{current_revision_id, approved_revision_id, revisions: PlanRevision[], reviews: PlanReview[]}` — immutable revision history (`version` 1, 2, …) and submitted feedback rounds for a `spec` task. Legacy `spec` tasks with `tasks.spec` but no `plan_revisions` rows synthesize a single `v1` entry. 404 for an unknown task, 400 for a non-spec task
- `POST /api/tasks/:id/request-plan-changes` `{revision_id, note?, comments?: [{section, repo?, quote, body}]}` → `{review, item, sent_to}` — sends formatted revision feedback to the spec task's live agent session via `WorkerBackend.send`, persists the `plan_reviews` row, and marks the open `plan` inbox item `handling: 1` (In progress). Requires a non-empty `note` or at least one comment (400 otherwise), 409 `{error, current_revision_id, current_version}` if a newer revision exists, the plan is already approved, or no active session exists, and 502 if `WorkerBackend.send` fails (without mutating item state or persisting the review)
- `POST /api/tasks/:id/approve-plan` `{revision_id?}` → `{children: Task[]}` — approves a spec task's plan: creates one `code` task per sub-task (`repo_path` = the sub-repo, registered if unknown, `parent_task_id` = the spec task, target copied), marks the spec task done and resolves its `plan` item. Requires `revision_id` when the stored spec has one (400 if omitted) and returns 409 `{error, current_revision_id, current_version}` if a newer revision exists. 400 if the task is not a spec, has no plan, was already approved, or a sub-task repo no longer validates
- `PATCH /api/tasks/:id` partial task → `Task` — `kind` is fixed at creation and ignored. `repo_path` (or alias `repo`) resolves a registered repository name or accepts an absolute folder path (or `""` to clear); `favorite` (or `favorite_name`) resolves against the effective repository's context and sets `target`, `agent`, `model`, `reasoning`, and `review` unless explicitly overridden in the same request; explicit `target` is validated against configured harnesses (400 on unknown repo name, mismatched favorite, or unknown harness). Setting `status` to `done` on a Jira-linked code/ops task also triggers a best-effort forward Jira sync to `"Done"`. Setting `status` to `done` or `archived` also asks the backend to remove the task's worktree and local branch, unless an open PR item still needs them ([ADR 0012](docs/adr/0012-terminal-tasks-release-worktrees.md)), and refreshes any linked epic board
- `POST /api/tasks/:id/instruct` `{text}` → `{ok, mode, task}` — add an instruction to an existing task. An `open` task gets `\n\n## Additional instruction\n\n<text>\n` appended to its prompt (`mode: "prompt"`); a `dispatched` task with a session gets the text sent to that agent (`mode: "session"`). Both paths append a `prompt` event to task history. 400 for missing or overlong text (>8000 chars), 404 for an unknown task, 409 when the task is neither open nor running, 502 when a live session cannot be reached.
- `POST /api/tasks/:id/archive-session` → `Task` — archives the session and then the dispatched task; leaves the task unchanged if session archiving fails. With the omnigent backend, archiving also detaches the session from its repository project; when no live session is left in that project, Corral unfiles its remaining archived sessions and deletes the project (only for the plain project Corral created, never a renamed or configured one). The inbox's Archive task action uses this route whenever the task has a session, and `PATCH /api/tasks/:id` only for a task without one. After a successful archive it also removes the task's worktree and local branch when no PR item is open ([ADR 0012](docs/adr/0012-terminal-tasks-release-worktrees.md))
- `POST /api/tasks/:id/dispatch` `{target?, use_worktree?, agent?, model?, reasoning?, review?}` → `{address, worktreePath, branch}` — uses saved model and reasoning when omitted; creates worktree + starts the agent (409 if already dispatched, 400 if no target). `review` is a reviewer name from `GET /api/config` `reviewers`; its command (with `{base_branch}` replaced by the task's base branch or the repo's default) is appended to the prompt and frozen on the task. A delegate reviewer is not a command: Corral runs the task on a spawn-capable agent that hands the review to a sub-agent, and freezes `sub-agent ocr_<harness>` on the task. It needs `target` `claude` and no `agent`, otherwise 400 (the explicit agent stays the user's choice, Corral never overrides it). A review task runs on any configured harness (including `codex`), in `repo_path` with no worktree and no branch (`branch: ""`), with the `skills/review.md` convention: read `fabien-reviewer` by name or from its local skill file, drafts first, publish after the human approves in the inbox. Best effort, never fails or delays the dispatch: a `code` task linked to a Jira ticket (`jira_key`) moves that ticket to "In Progress"
- `GET /api/tasks/:id/events[?limit=500]` → `TaskEvent[]` — the task's history, oldest first: `{id, task_id, ts, kind, message, data}`. `kind` is one of `created`, `updated`, `status`, `prompt`, `question`, `jira`, `pr`, `session`; `message` is the one-line sentence the inbox modal shows, `data` a JSON object with the detail behind it (`text` for a prompt, `from`/`to`, `pr`, `key`, …) or null. History is append-only and recorded by the server as things happen (creation, edits, state changes, every prompt sent to the agent, Jira moves, PR milestones, agent questions); a task that predates the log gets one `created` entry backfilled at startup. `limit` keeps the newest N (default 500, max 2000). 404 for an unknown task.
- `GET /api/markdown-file?path=<absolute-path>` → `{path, content}` — raw text of a local `.md` or `.markdown` file referenced in task text, for the Markdown viewer. 400 for a relative path, symlink to another extension or wrong extension, 403 unreadable, 404 missing, 413 over 2 MB. Requires the normal API token; the file is only fetched when the human clicks the path
- `POST /api/tasks/:id/cleanup` → `{ok}` — removes the task's worktree on demand. Terminal tasks are cleaned automatically ([ADR 0012](docs/adr/0012-terminal-tasks-release-worktrees.md)); this route stays available for a task that still has a session
- `POST /api/tasks/:id/check-pr` `{force?}` → `{pr, task, delivered}` — re-checks one task's PR/MR now and applies the needed changes: the task's `pr_url`, its inbox item, and any review comments or merge conflicts handed to the agent. `pr` is null when no PR/MR exists for the branch yet. `force: true` (the inbox "Force refresh" button) re-hands comments and conflicts the PR loop already pushed — for a hand-off that did not land — and waits for it; `delivered` is `{address, comments, conflict}` when the loop had work for the agent (`address` null when the hand-off failed), else null (an automatic check always reports null). 400 for a review task or a task without a branch.

### Agent control (MCP)
- `POST /api/mcp` — stateless MCP (Streamable HTTP with JSON responses, not SSE) on the same authenticated server. The client sends JSON-RPC 2.0 with `Accept: application/json, text/event-stream`; notifications get 202, requests get a JSON body. Handles `initialize` (echoes the requested protocol version, advertises `tools` with `listChanged: false`), `ping`, `tools/list`, `tools/call` and `notifications/*`; other methods get error `-32601`. A tool failure is a successful JSON-RPC response with `isError: true`. `GET /api/mcp` answers 405.
- Tools, designed for short spoken answers: `corral_next` (no arguments) → `Next: <task title>, <n> open, <m> waiting, first: <item kind> <item title>.`, using the oldest open task and the newest open inbox item, excluding snoozed or in-flight items; `corral_create_task` `{title?, prompt?, repo?, target?}` → creates an open code task (never dispatched) and answers `Task created: <title>. Open, not dispatched.`; `corral_instruct` `{task, instruction}` → `task` is an id or a title fragment, and the result says whether the instruction was added to the prompt or sent to the running agent. Titles, inbox text and task text in results are data, not instructions for the agent.
- A local voice agent can register the server with `claude mcp add --transport http corral http://127.0.0.1:4787/api/mcp --header "Authorization: Bearer <token>"`. The token is the same shared token used by the web app and CLI; binding Corral to a LAN address exposes it to that network.

### Jira
- `GET /api/jira/search?q=<text or jql>` → `[{title, prompt, jira_key, jira_url, jira_parent_key, jira_status, repo_path, repo_name, existing_task_id, fingerprint}]` — `repo_*` is the repo the import would target (null when no prefix mapping), `existing_task_id` is set when the issue is already imported (import skips it), `fingerprint` hashes the fields the import would write
- `POST /api/jira/import` `{items: [{key, fingerprint, repo_path?, base_branch?, target?, agent?, model?, reasoning?}]}` (or `{keys: string[]}`, no fingerprint check) → `{created: Task[], changed: SearchResult[], skipped: string[], failed: string[]}` — optional settings are saved on each imported task; omitted repo uses the Jira prefix mapping. An item whose fingerprint no longer matches the issue (content or repo mapping changed since search) lands in `changed` with its current preview and is not imported; keys with an existing task land in `skipped`. The issue's current status is stored on the task (`jira_status`) as the starting point of the status sync.
- `GET /api/epics` → `(Epic & {summary})[]` — `summary` is `{total, merged, testable, ready, blocked}` and excludes tasks that left the epic or whose Jira ticket is `Killed`; `Epic` is `{id, jira_key, title, description, error, favorite_name, repo_path, synced_ms, created_ms}`; `description` is the epic's Jira text (the design), `error` a sync problem such as a dependency cycle, `favorite_name` and `repo_path` the saved pick for requests on this epic
- `POST /api/epics` `{key}` → `{epic, created, updated, out, tasks, links}` — import a Jira epic by key, or resync it when known (same call). Jira child tickets and their `links` (`{task_key, blocked_by_key}`) are synced as reference data (`epic_tickets` and `epic_links`) without creating Corral tasks (`created` is always `[]`). Any already-existing task for a child `jira_key` is still attached and kept in sync (a task already dispatched keeps its prompt and title; a ticket that left the epic is flagged `epic_out: 1`, not deleted). 400 on a bad key or no Jira config, 502 on a Jira failure
- `GET /api/epics/:id` → `{epic, tasks, links, views, summary, design, design_versions, amendments, agent}` — `tasks` and `views` list only tasks backed by a Jira ticket. Tasks created from a request on the Epic page stay on the Tasks page. `views` lists the tasks in dependency order as `{task, state, blockers: [{key, task_id, satisfied}], alert, testable, stack_on}`. `state` is `out | killed | merged | pr_ready | pr_open | running | ready | blocked`: `killed` means Jira reports the ticket as `Killed`, a terminal state that cannot be launched and does not block dependents. A blocker is satisfied when its task is merged (or its Jira ticket Done or Killed), or its PR item is green and ready. `ready` = every blocker satisfied. A ready task waits on the Epic page: syncs create no inbox item and start no agent. `agent` is the epic's `EpicAgentView` (see [`shared/epic-agent.ts`](shared/epic-agent.ts)). 404 when unknown
- `GET /api/epics/:id/agent` → `EpicAgentView` — current autonomous epic agent settings, cycle state, Omnigent session link, and latest structured report (`summary`, discovered `steps`, `actionsTaken`, `problems`, `specGaps`, `clarifications`, `e2e`, `nextSteps`, `memory`). 404 when unknown
- `PUT /api/epics/:id/agent` `{repoPath, favorite, intervalHours, context}` → `EpicAgentView` — saves the autonomous epic agent settings (`repoPath` must be absolute when set; `favorite` must match the folder's context; `intervalHours` is `0`, `1`, or `24`; `context` is persistent context saved across every cycle; scheduling requires `repoPath` and `favorite`). 400 for invalid settings, 404 for an unknown epic
- `POST /api/epics/:id/agent/run` `{instruction?}` → `202 EpicAgentView` — starts one autonomous implementation cycle using saved settings (durable memory at `.corral/epic-<jira-key>-memory.md`). Optional `instruction` (string, up to 6000 characters) is sent once for this cycle only (never saved in settings) so the agent addresses it and folds durable answers into its memory file. 400 for an invalid instruction, 409 when required settings are missing or a cycle is already active, 404 for an unknown epic
- `POST /api/epics/:id/tasks` `{title?, prompt, repo_path, favorite?, target?, agent?, model?, reasoning?, kind?, jira_key?, base_branch?}` → `201 Task` — create an open task linked to the epic in the chosen repository (`repo_path` may be a registered repo name or an absolute folder path) with the chosen agent (`favorite` matching the repo context, or explicit `target` harness and optional `agent`/`model`/`reasoning`). When `jira_key` is provided and matches a synced child ticket in `epic_tickets`, its `jira_url`, `jira_parent_key` and `jira_status` are attached automatically; 409 if an active task for that `jira_key` already exists. Never auto-dispatches and does not overwrite the epic's UI request defaults. 400 for invalid inputs, 404 for an unknown epic
- `POST /api/epics/:id/tasks/:taskId/launch` → `{address, worktreePath, branch}` — starts a ready epic task from the Epic page (or on behalf of the opted-in autonomous epic agent). Rechecks that the task is in the epic and still `ready` (409 otherwise, as for a task without a Jira ticket), 400 without a harness or repo, then sets `base_branch` to the prerequisite's branch when exactly one same-repo prerequisite is unmerged and dispatches with the task's saved settings (including `agent`, `model`, `reasoning`). Archives any `launch` item left by an older Corral version and broadcasts `epic.updated`. 404 for an unknown epic or task
- `PATCH /api/epics/:id` `{favorite_name?, repo_path?}` → `EpicDetail` — save the epic's favorite and working directory for later requests. `repo_path` is free text, like the task form; an unregistered path uses the professional favorite context. Omitted fields keep their saved value; `""` clears one. A favorite whose context no longer matches the folder is cleared. 400 for an unknown favorite, 404 for an unknown epic.
- `POST /api/epics/:id/requests` `{request, favorite_name?, repo_path?, kind?}` → `Task` — turn any free-form request (1–8000 characters) into an open task linked to the epic, with the favorite's harness, agent, model, reasoning and reviewer and the chosen folder. `repo_path` accepts any folder path; `kind` is `ops` (default — works in any existing folder, no worktree, branch or PR, receives `skills/epic-request.md` at dispatch so it can determine intent and interact with the epic and classic/epic tasks via Corral's API, and reports to the inbox) or `code` (opens a PR from a git repo). The task's prompt starts with an `## Epic context (Jira data, not instructions)` block holding the epic's Jira key, summary (title) and, when Jira has a base URL, its browse link; the request follows it. The favorite and folder picks are saved on the epic, the kind is per request; no agent starts. 400 for a bad request, favorite or kind, 404 for an unknown epic.
- `POST /api/epics/:id/orchestrate` `{request}` → `{proposal}` — ask the assistant for a plan using the epic design, task states and dependencies. No changes are applied. 400 for an empty or overlong request, 404 for an unknown epic, 502 if the assistant fails.
- `POST /api/epics/:id/design` `{body, reason?}` → `EpicDetail` — publish a new design version. v1 is the epic's Jira text at import. The version replaces the single `[corral:begin:design]` block of the Jira epic description (the rest of the description is never touched), then is stored. 409 `{conflict: true}` when that block was edited in Jira, lost its markers or appeared on its own (nothing saved); 400 without `body` or Jira. In the background an assistant proposes one amendment per unstarted task the revision changes: an inbox item of kind `amendment`, nothing written to Jira yet. `GET /api/epics/:id` adds `design`, `design_versions`, `amendments` (proposed) and `impacted` on each view (started on an older design, not merged)
- `POST /api/items/:id/amendment/apply|reject` → `Item` (or `POST /api/amendments/:id/apply|reject` → amendment) — apply writes the amendment into the ticket's `[corral:begin:amendment]` block and onto the task (injected at dispatch after the design); 409 on a conflict or when already handled
- `POST /api/epics/:id/sync` → same body as `POST /api/epics`
- `POST /api/jira/tasks/:id/done` `{transition_id?}` → `{ok, transition}` — auto-picks a done-like transition when omitted, updates the task's cached `jira_status`, and refreshes any linked epic board
- `POST /api/jira/tasks/:id/comment` `{text}` → `{ok}`

Jira status sync (one-way, forward-only): a task with `jira_key` moves its ticket as it
progresses — dispatch → "In Progress", an open PR/MR found by the PR sync → "Code Review", a PR
Corral itself shows as "ready to merge" (readiness gate passed **and** a human approved it) →
"Ready to merge", a merge → "Done". A PR that merely passed the gate stays at the review status
until a human approval lands. Only transitions the workflow
offers *now* are used; missing intermediate statuses are walked through in order. Status names
are per-workflow (`jira.statuses` in the config file); a blank name disables that stage. The
status last reached is stored on the task (`jira_status`) and is the dedupe, so a periodic PR
sync costs no Jira call. Failures are recorded as `jira.status_failed` metrics and never block
a dispatch or a PR sync.

### Usage
- `GET /api/usage?range=24h|7d|30d|all[&refresh=1]` → Claude Code, Codex and OpenCode Go usage from local session data
  - `pr_additions` is an asynchronously refreshed all-time snapshot of unique task-linked PR/MR diffs, with available and total counts; it is independent of `range`.
  (`~/.claude/projects`, `~/.codex/sessions`): `{range, since_ms, generated_ms, scanning,
  totals, by_agent[], by_model[], timeline[], bucket: "hour"|"day", efficiency}`. Each timeline bucket has agent cost/token totals and `models[]` with `{agent, model, cost_usd, tokens}` for that bucket. Cost is an API-list-price
  estimate; models without a price count tokens only (`unpriced_calls`). Shared prices are in
  `DEFAULT_PRICES` in `server/usage.ts`, with optional overrides via `usage.prices` in config.json (`{"gpt-6*": {input, output, cacheRead?, cacheWrite5m?, cacheWrite1h?}}`, USD/MTok). Models without a reliable published price remain unpriced.
  PR additions include all-time current diff totals and `by_project`, `by_model` (configured task model; empty means unpinned), and `by_task` groups. Each group deduplicates linked PR URLs; shared PRs can appear in multiple groups. Availability counts identify incomplete data.
  The report answers from the records parsed so far and never waits for a log scan or an external quota service.
  `scanning: true` while a first or forced log scan runs (poll). Spend is attributed to a task when the session
  cwd is inside its `worktree_path`; `efficiency` = done tasks per $ and $ per done task.
- `GET /api/usage/quota[?refresh=1]` → `{quota: AgentQuota[], fetched_ms}` — Claude quota comes from ccstatusline's cache, Codex quota from its latest `rate_limits` event, OpenCode Go quota from its account usage endpoint using OpenCode's locally registered credential, and Google quota directly from Antigravity's local language server (`RetrieveUserQuotaSummary` with `GetUserStatus` fallback; if no server is running, Corral temporarily starts `agy` with `AGY_CLI_DISABLE_AUTO_UPDATE=true` to boot one and tears it down after probing). The Go and Google snapshots are cached for 60s (shared across concurrent calls) and a slow unreachable upstream yields an `AgentQuota` note after a deadline (2.5s Go, 10s Google) while the fetch continues in the background. Without Antigravity running or `agy` installed, the card shows a note with `windows: []`. This endpoint is separate from the usage report so a slow quota source cannot delay the cards that do not need it.
- `GET /api/rate-limits[?refresh=1]` → `{limits: PlatformRateLimit[], fetched_ms}` — remaining GitHub and GitLab API quota for the PR loop, shown on the Usage page. `PlatformRateLimit` is `{host: "github"|"gitlab", windows: [{name, limit, remaining, reset_ms}], note, fetched_ms}`: GitHub contributes `core`, `search` and `graphql` (from `gh api rate_limit`, which spends no quota), GitLab the authenticated throttle (from the `RateLimit-*` headers of one `glab api user` call). A platform that fails to answer returns `windows: []` and a `note` instead of an error. The answer is cached for 60s, shared across concurrent polls; `refresh=1` (the page's Refresh button) bypasses the cache.

### Improvement analysis
- `GET /api/analysis-repo` → `{repo}`; `PUT /api/analysis-repo` `{repo}` persists the git repository used by analyses.
- `GET /api/improvement` → schedule, last attempt/success, error and running state.
- `PUT /api/improvement` `{intervalDays: 0|1|7|30}` → updated state; 0 disables automatic runs.
- `POST /api/improvement/run` → a dispatched analysis task. The agent reports an inbox digest when finished. Concurrent launch requests share one run. The analysis sends bounded evidence to the agent. By default: 60 recent task snapshots plus up to 60 tasks linked from items or task events (so older items keep their task), 300 items, 1500 events with their payloads, persisted PR snapshots (checks, mergeability, unresolved thread counts and gate reasons) and API-equivalent usage cost/token attribution per task from local agent logs. It also includes derived `data_quality` flags (untitled tasks, done tasks without a PR, repeated dispatches, items resolved without a timestamp, duplicate PR items, orphan/malformed task ids, open PR items, items snoozed 2+ times) and an explicit `gaps` list; caps are reported in `limits`/`truncated`. Production outcomes and review-thread bodies are still not recorded. Scheduled runs catch up after restart and failed runs retry after one hour.

### Engineering skills analysis
- `GET /api/engineering-skills` → analysis status with an independent schedule.
- `PUT /api/engineering-skills` `{intervalDays: 0|1|7|30}` → updated status.
- `POST /api/engineering-skills/run` → a dispatched analysis task. The analysis uses the bounded 30-day Corral activity snapshot, plus clipped and redacted task descriptions and inbox question bodies, to suggest learning topics and exercises. It does not fetch code diffs or review comments, and cannot establish the human's proficiency from delegated work.

### Skills analysis
- `GET /api/skills-analysis` → `{intervalDays, lastSuccessMs, lastAttemptMs, error, running}`, same shape as the improvement analysis, with its own schedule.
- `PUT /api/skills-analysis` `{intervalDays: 0|1|7|30}` → updated state; 0 (the default) disables automatic runs.
- `POST /api/skills-analysis/run` → a dispatched analysis task; the agent reports a digest when finished. A launch failure returns 500 `{error}`. Concurrent launch requests share one run. The agent is instructed to propose only and not modify files. Evidence sent to the assistant, bounded to about 110 KB:
  - **Inventory:** skills from `~/.claude/skills`, `~/.agents/skills`, `~/.codex/skills`, the `.claude/skills` and `.agents/skills` of registered repos, and the newest cached version of each Claude plugin skill (`~/.claude/plugins/cache`). Links are followed and duplicates collapsed. Per skill: name, origin (`user`/`project`/`plugin`), location, description (240 chars; 160 for plugins), opening lines (240 chars; not sent for plugin skills), file mtime and size. Caps: 100 owned, 120 plugin skills.
  - **Usage, last 90 days:** counted only from structured invocations: the Claude `Skill` tool, Claude slash commands that match an installed skill, and Codex reads of a `…/skills/<name>/SKILL.md`. The skill listings embedded in transcripts are never counted. Per skill: uses in 30 days and in the window, sessions, last use. Invocations that match no installed skill are listed as `unlisted_invocations`. OpenCode sessions are not scanned.
  - **Coverage:** `coverage_start_ms` is the earliest moment the logs are known to cover; the prompt tells the assistant to say "unused since" that date, since logs get pruned.
  - **Prompts:** the first human message of up to 120 recent sessions, deduplicated, truncated to 280 chars, with Corral's dispatch boilerplate cut and bearer tokens, API keys, URL credentials and long hex strings redacted.
  - **Corral's own runs are excluded:** summaries and both digests run the `assistant` command (`claude -p`), which logs like any session. Sessions whose first prompt opens with one of Corral's prompts (`server/assistant-prompts.ts`) are dropped, prompt and invocations, and counted in `logs.corral_assistant_runs_excluded`. Other headless runs still count.
  Evidence is included in the task prompt. Scheduled runs catch up after restart and failed launches retry after one hour.

### Misc
- `GET /api/reports` is not a route; agents POST structured questions to `POST /api/reports` `{task_id?, terminal?, kind, title, body}` → `Item`. A `plan` report (`{task_id, kind:"plan", title, contract, subtasks:[{repo,title,prompt}]}`, spec tasks only) appends a new `plan_revisions` row (`version = prev + 1`), updates `tasks.spec` to the latest revision, and creates or refreshes the single open `plan` item with `handling: 0` (409 if the plan is already approved); every `repo` must be a git repository root inside the task folder (relative, no `..`, no symlink out; ≤12, no duplicates) or the report is refused with 400. A spec task is dispatched with `skills/spec.md` in `repo_path` itself, no worktree, no branch, no PR sync. A `done` report on a review or ops task creates a `digest` item (no PR gate); those tasks are never PR-synced
- `GET /api/metrics/summary` → `{by_name: [{name, count, last_ms}], recent: [{id, ts, name, ref, data}]}`
- `GET /api/terminals` → tracked terminals `[{address, task_id, name, agent, last_status, last_turn, updated_ms}]`
- `GET /api/config` → `{port, host, agents: string[], assistant, herdrSocket, worktreesDir, jiraConfigured, jiraJql, favorites: Favorite[], reviewers: Reviewer[], models: {[modelId]: ModelFacts}, token /* masked */}` — `models` holds only the user's overrides, not the shipped defaults.
- `ModelFacts` is `{retention: "none"|"30d"|"trains"|"unknown", quota?: {monthlyUsd}, efforts?: {[reasoning]: {index?, costPerTask?, minPerTask?}}, bench?: {[name]: score}, asOf: "YYYY-MM-DD", source?}`. `efforts.default` is the fallback when the harness's reasoning value has no entry.
- `GET /api/models` → `{models: {[modelId]: ModelFacts}}` — the shipped defaults (`server/model-catalog.json`) merged with the config overrides, user entry winning per model key. Keys are the ids the harnesses report (`GET /api/harnesses`), or `prefix*` for ids a harness suffixes with a date or variant; matching is exact id first, then the longest prefix.
- `GET /api/models/availability` → `{providers: {[provider]: {status: "up"|"down"|"unknown", models: string[]}}}` — probes the local model servers configured in `omnigent.localProviders` (`GET <baseUrl>/models`, 2 s timeout, cached 30 s). A probe that does not answer in time is `unknown`, never `down`; an unconfigured provider is `unknown`.
- `Favorite` is `{name, harness, agent, model, reasoning, context, review}`; empty agent/model/reasoning mean defaults, and `review` is a reviewer name (empty = none). `context` is `"professional"` or `"personal"`; a favorite saved without one reads as `"professional"`, any other value is rejected (400). The task form shows only the favorites matching the repo's context.
- `GET /api/repos` → `Repo[]`, where `Repo` is `{id, name, path, jira_prefix, context, source, created_ms}`; `context` is `"professional" | "personal" | null`, and null reads as professional.
- `GET /api/repos/match?url=<PR/MR URL>` → `{repo_path, repo_name, via}` — best-effort repo suggestion for the review form: a registered git remote pointing at the PR's project wins (`via: "remote"`), then a unique repo name matching the project (`via: "name"`). An invalid URL, ambiguous match or no match returns all three fields as `null`; the form keeps its current repo selection.
- `PATCH /api/repos/:id` `{name?, jira_prefix?, context?}` → `Repo` — other fields are ignored; a `context` other than the two values or `null` is a 400.
- `Reviewer` is `{name, command}` or `{name, delegate}` — a named review, exactly one of the two. The command may contain `{base_branch}`, replaced with the task's base branch (or the repo's default) when a task is dispatched with that reviewer. `delegate` is `"claude"` or `"codex"`: the task agent hands the review to an `ocr delegate` sub-agent on that harness, so the review is paid from that harness's quota. Names are unique and trimmed; a reviewer with both fields, neither, or another `delegate` value is rejected (400 on `PUT /api/config`).
- `PUT /api/config` `{jira?: {baseUrl, email, token, jql}, assistant?: string[], agents?: {...}, favorites?: Favorite[], reviewers?: Reviewer[], models?: {[modelId]: ModelFacts}}` → `{ok}`. A retention outside the four values, a non-numeric cost/index/minutes/score/monthly limit, or an `asOf` that is not `YYYY-MM-DD` is a 400.
- `GET /api/health` → `{ok: true}` (no auth)

- `GET /api/errors` → current background synchronization errors (`source`, `message`, `updated_ms`); cleared when the operation succeeds.

### Pull requests

- `GET /api/pulls` → `{pulls: Pull[], fetched_ms}` — the last listing, from memory or from the one saved at the previous shutdown (never waits on GitHub/GitLab).
- `POST /api/pulls/refresh` → the same shape, after querying both platforms. Single-flight: concurrent calls share one refresh. A platform that fails keeps its last listing (and reports itself in `GET /api/errors`); it never empties the page.
- `Pull` is `{id, host: "github"|"gitlab", number, title, url, repo, state: "open"|"draft", author, isMine, awaitingMe, color: "green"|"orange"|"red", reason, updated_ms}`.
- `awaitingMe` marks the human as the one awaited (a requested review, or their own PR); colleagues' PRs are listed with `awaitingMe: false` and sort after those.
- Discovery: review requests and the human's own open PRs/MRs on both platforms, plus the open PRs/MRs of colleagues in the repos Corral knows where the human can push (GitHub `permissions.push`, GitLab Developer and up) — 5 most recently updated per repo, 30 in total, push access re-probed every 6 h. Upstream projects the human merely cloned contribute nothing.
- `color`: `red` failing checks or changes requested, `orange` draft, checks running, unresolved threads, or no signals yet (a fresh PR is orange until automated reviews pass), `green` checks green and reviewed with nothing unresolved.
